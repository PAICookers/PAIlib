# PAIlib 稳定版发布准备

目标是产生可审阅的发布准备改动和验证记录，不把本地检查通过等同于已发布。
所有项目路径均相对仓库根目录；本技能内的参考链接相对本技能目录。
先通过 Git 确认根目录、分支、已有改动和目标版本，不依赖调用者的工作目录。

## 确定本次范围

- 用户仅要求审查时保持只读；要求准备时更新相关文件。本技能的执行本身不授权
  提交、推送、合并、打标签、发布 GitHub Release、上传 PyPI 或修改远端设置。
  如用户另有明确授权，完成本地检查后再执行所授权操作。
- 用户明确要求“release-ready”“自行完成更新”或“准备稳定版”时，进入准备模式：
  在保留无关工作区修改的前提下，直接更新本技能列出的发布文件、开发说明和 CI
  配置，随后运行验证。不要把可由仓库事实确定的文件编辑退回给用户；只有版本
  语义、硬件含义、远端权限/保护、候选提交范围或事实不足等真正存疑处才暂停或
  列为待确认项。仅说“检查/审查”仍是只读模式。
- 以 `git status`、本地标签和提交记录为起点；可访问远端时再核对标签、发布状态和
  CI。识别最近稳定版本及其对应提交，以其后的真实差异归纳变更，不能只看版本号。
  远端不可访问时记录证据缺口，不宣称版本未占用或远端检查通过。
- 用户指定的目标版本优先，必须是无预发布/开发/本地后缀的稳定 `X.Y.Z`。
  未指定时从兼容性和现有发布记录提出版本；写版本前让用户确定，继续做独立检查。
  不擅自选择破坏性升级号，不把当前已发布版本当成下一版本。
- 按仓库现有分支策略决定工作区；保留无关修改，不主动切换调用者分支。
  使用 `git ls-files` 发现共享文件；新建的发布文件可以纳入本次交付，但不能依赖
  本机未跟踪脚本、个人任务记录、私有资料目录或全局安装的其他技能。

### 准备模式的确定性更新

- 从最近稳定 tag 到当前候选提交归纳变更；只写入已存在代码、测试或提交证据
  支持的说明。测试/静态检查通过不能升级为真板、性能、准确率或全模型证据。
- 目标版本已明确且符合 `X.Y.Z` 时，更新 `pyproject.toml` 的 `project.version`，
  重新生成/校验 `uv.lock` 的项目版本，并检查包级版本读取保持单一来源。若目标版本
  与最近稳定版的兼容性含义仍无法判断，继续完成机械检查并把版本语义列为存疑，
  不凭空选择 major/minor/patch。
- 在 `CHANGELOG.md` 顶部新增完整目标稳定版本区块，保留现有历史区块内容；修复
  已确定的仓库内坏链接。同步 README 双语中已经由候选代码提供且可准确描述的公共
  能力、限制和相对链接；不把接口猜测、未验证硬件或未来计划写成事实。
- 对明确错误且内容已由仓库事实确定的发布自动化配置（例如 Dependabot 放错目录、
  workflow paths 漏掉发布配置）做最小修复。不要顺手升级 Action、runner、依赖或
  认证设置；远端环境、OIDC、保护规则和 secrets 只检查并报告，不代替管理员修改。
- 显式保留 `.codebase-memory/artifact.json` 的未跟踪且未忽略约定；显式选择文件时
  不使用 `git add .`。准备模式也不自动提交、推送、建 tag、建 Release 或发布包。

## 按需读取与更新

先读 `pyproject.toml`、`CHANGELOG.md`、现有 README，以及存在的共享开发规范。
其余文件仅在对应检查适用时读取；不扫描全部历史任务或加载整库源码。

| 检查面 | 读取范围与更新目标 |
| --- | --- |
| 用户说明 | `README.md`、`README_EN.md`、涉及功能的 `docs/`；同步安装要求、公共 API、兼容性、迁移示例和相对链接，中文主文档优先 |
| Agent 与开发规范 | 存在时读取根 `AGENTS.md`、贡献指南和仓库共享规则；核对目录图、公共入口、Python 范围、测试命令与实际工具。缺少规范时，准备模式补充最小共享说明，审查模式仅提出方案；不引入个人路径或照搬其他项目规则 |
| 版本与打包 | `pyproject.toml`、`uv.lock`、包级版本来源及版本测试；读取下述清单的“版本和产物”部分 |
| 发布说明 | 完整版本级 CHANGELOG 区块、发布基线之后的提交与差异；遵循下述排序约定，不把草稿、提案或未执行实验写成已完成 |
| 代码索引 | 存在时读取共享索引约定，检查当前检出目录的索引状态；按下述方法按需刷新 |
| CI/CD | `.github/workflows/`、`.github/release-drafter.yml`、`.github/dependabot.yml`、`.pre-commit-config.yaml`、`ruff.toml`；读取清单的“自动化”部分 |

细节集中在 [references/release-checklist.md](references/release-checklist.md)：
检查打包/版本时只读“版本和产物”，检查 CI/CD 时只读“自动化”；执行验证或出具
结论时再读“验证与交付”。配置和公开工具接口发生变化时查安装版本帮助或官方文档，
不要为消除通知而机械升级所有依赖、Action 或系统镜像。

### CHANGELOG 的固定约定

- **最新稳定版本的说明在所有历史版本之前；其余版本按版本号升序排列。**
  例如发布 `2.1.0` 后为：`2.1.0 → 1.0.0 → 1.1.0 → 2.0.0`。
  因此此前置顶的 `2.0.0` 必须回到历史序列末尾，不能继续留在 `1.0.0` 前。
- 比较数值版本/标准版本语义，不能按字符串排序（`1.10.0` 大于 `1.9.0`）。
  保留历史中实际存在的预发布、撤回标记、日期和内容；预发布用标准版本解析器排序。
  无法解析的标题先核对，不擅自丢弃或猜序。
- 移动完整版本区块，包含其三级标题、正文和关联引用；同一版本不得重复。
  如有 `Unreleased` 草稿，默认在最新稳定版之后、历史版本之前保留独立区块；
  只把本次确实交付的内容转入新稳定版，不把未完成计划算入发布。
- 以用户可感知的新增、修复、破坏性变更、工程化和迁移影响组织说明。
  保留事实与证据边界，测试通过不能推导出真板、性能或所有硬件均验证。

### 代码索引的按需检查

- 有 codebase-memory MCP 时先用 `index_status` 确认索引所属根目录与新鲜度。
  支持时使用 `project="@current"`；不支持时发现准确项目名并核对 `root_path`，
  不写死某位开发者的项目名或绝对路径。没有工具时使用当前源码并报告索引未验证。
- 源码结构/导出/调用关系变化、切换版本导致索引过期、索引缺失或明确要求时刷新；
  只有文档或版本元数据变化且代码索引仍有效时，不必无条件重建。
  刷新根目录从 `git rev-parse --show-toplevel` 得到，使用持久化索引；
  异步刷新必须等到完成，再检查解析缺口、相关路径覆盖并抽查变化符号。
- 结构查询用 `search_graph` 定位、`trace_path` 查影响、`get_code_snippet` 看定义，
  结果先限制到有关模块；用 `check_index_coverage` 检查证据路径，缺口回读源码。
  空结果不证明代码不存在；索引不证明行为正确。遵循服务器对读别名的适用限制。
- 共享图文件采用 `.codebase-memory/graph.db.zst`；若作为交付物更新，只显式选择
  图文件和必要的共享配置。**`.codebase-memory/artifact.json` 保持未跟踪且未忽略**，
  不新增忽略规则，也不通过 Git 标志隐藏。分别用 `git ls-files` 与 `git check-ignore`
  核实两种状态；若现状违背约定，报告并仅在用户授权的范围内纠正。

## 完成标准

按检查清单完成本次授权范围内的更新；对尚未具备的环境/远端证据给出明确缺口。
检查项不是自动放行：版本不一致、阻断测试失败、打包缺件、发布触发链错误等仍需
修复或标明阻塞。普通迁移通知与真实失败分开判断。

交付简短列出：目标版本和基线、改动文件、通过/失败/未执行的检查、索引状态、
CI 证据对应的提交，以及发布前仍需处理的事项。不能凭旧提交的绿灯放行新提交。
